How Endless Sky Works

A plain-language tour of a space sandbox that ships twice as much text as code — written for programmers who have never touched C++ or this codebase.

endless-sky 0.11.3 · 481 source files · 204 data files · C++20 · read from this checkout

Endless Sky is a 2D space sandbox in the lineage of Escape Velocity: you start with a small ship and a large loan, and trade, fight, explore or follow a storyline from there. This page is about the program, not the game — how it is organised, and why.

You do not need to know C++. Where a C++ idiom matters, it is explained in passing. What you do need is to accept one inversion early, because nearly every design decision in this codebase follows from it.

1What kind of program this is

Open the repository and count lines. There are about 120,000 lines of C++ under source/. There are about 262,000 lines of plain text under data/. The content outweighs the engine more than two to one, and that ratio is the architecture in one number.

The C++ does not know what a Kestrel is. It does not know that Earth exists, that the Republic is at war, or that a jump drive lets you leave the hyperspace network. Every one of those is a line of text parsed at startup. The program is an interpreter; the universe is its input.

This is not a mod system bolted onto a finished game. It is the only way the game is built: the official campaign loads through exactly the same path a third-party plugin uses, from exactly the same file format, with no privileged position of any kind. A plugin is simply another directory handed to the same loader.

That single decision explains most of what follows. It is why definitions are looked up by name rather than by pointer or index; why redefining something merges into it rather than replacing it; why the game carries a general-purpose "conditions" namespace that looks over-engineered until you realise data files need some way to ask the engine questions; and why the file format has to stay readable enough for a writer with no programming background to work in all day.

The shape of the whole program

Three sources of definitions, one loader, one shared universe, and a strict discipline about who may write to it once loading is done.

C++ in sixty seconds, if you need it

C++ splits code across two kinds of file. A header (.h) declares what exists — names, types, shapes — and other files "include" it to learn about them. A source file (.cpp) holds the implementation. Including a header is a literal textual paste, which is why GameData.h appearing in 95 files makes it expensive to change.

One more C++ fact bites constantly here: nothing is discovered automatically. Every source file must be listed by hand in the build configuration, or it is silently never compiled — no error, no warning, just a missing symbol much later. This project guards that with a dedicated script, precisely because the failure mode is invisible.

3One text format, for everything

Learn the file format before anything else, because it is the interface between almost every part of this project. Game content, saved games, plugins, preferences and the integration test suite are all written in it, and all parsed by the same two classes.

The rules fit in four lines:

  • A node is one line of whitespace-separated tokens.
  • Its children are the lines indented one tab further.
  • Double quotes group words into a single token; backticks group text that itself contains quotes.
  • The first token names the kind of thing, and usually the second is the name it is filed under.
ship "Aerie"
    sprite "ship/aerie"
    attributes
        category "Medium Warship"
        "cost" 3500000
        "shields" 5700
    outfits
        "Heavy Laser Turret" 2
        "NT-200 Nucleovoltaic"

In C++ that arrives as a DataNode: a list of tokens you read with Token(i) for strings or Value(i) for numbers, plus a list of child nodes. Every loader in the codebase has the same shape — a Load(const DataNode &node) that walks its own tokens, then loops over the children and dispatches on their first token, recursing down. Read one Load function and you can read all of them.

The format is deliberately forgiving about what it does not recognise, and deliberately loud about it: an unknown key produces a warning naming the file, the line and the enclosing nodes, rather than a failure. A plugin written against a different version of the game degrades instead of crashing.

4How a universe assembles itself

Here is the trick that makes the whole data-driven design work, and it is four lines long. Every kind of definition lives in a Set, and asking a Set for something by name looks like this:

template<class Type>
class Set {
    Type *Get(const string &name) { return &data[name]; }
    // ... data is a std::map<string, Type>
};

In C++, indexing a map with a key that is not there does not fail — it creates an empty entry and returns it. So Get("Kestrel") always succeeds, whether or not any file has defined a Kestrel yet, and the pointer it returns stays valid for the life of the program.

Three large consequences fall out of that one line:

  • Load order does not matter. A mission can point at a planet defined in a file that has not been read yet. It gets a pointer to the blank planet, which fills in later.
  • Circular references are free. A system lists its planets; each planet names its system. Neither has to exist first.
  • A typo produces a ghost. Misspell a ship name and you do not get an error — you get a pointer to an empty ship that nothing ever fills in.

That last one is why loading has a third phase. CheckReferences() runs after all files are read and sweeps the sets for objects that were referred to but never defined, reporting them. It is the safety net under the convenience.

Redefining merges; it does not replace

Load a ship "Aerie" node when an Aerie already exists and its fields are written over the existing object. Anything the second definition does not mention keeps its old value. This is the mechanism behind plugins that patch the base game: a four-line file that adjusts one ship's shield value leaves the other forty fields alone.

When you genuinely want a clean slate, an overwrite line before the definition resets the object first:

overwrite
ship "Aerie"
    // starts from a blank Aerie, not the shipped one
Where this bites Because merging is the default, a plugin that removes something cannot do it by redefining the thing as empty. Subtraction has to be expressed by the game's own vocabulary — remove and unlink nodes, or an event that changes the universe — not by omission.

The three phases of loading

PhaseWhat happens
BeginLoad()Directories are walked and files parsed, spread across a pool of worker threads. Sprites and sounds stream in alongside. This is what the loading screen is measuring.
FinishLoading()Cross-references are resolved: neighbouring systems computed, wormhole requirements worked out, derived values filled in.
CheckReferences()Everything referred to but never defined is reported. Nothing is fixed here — it is a diagnostic pass.

And then, because stories mutate the world, there is a fourth operation that is not part of loading at all. Revert() walks the current sets against a pristine copy, deletes anything that was added and restores anything that was changed. It runs when you switch pilots, and it is the reason one character's finished war does not leak into another's galaxy.

5Conditions: the seam

A data file can define a ship. But how does a data file ask a question — whether the player has 50,000 credits, or has visited Earth, or is flying a warship? The answer is one flat namespace of named integers called conditions, and it is the single most important interface in the codebase.

Every condition is a string mapped to a 64-bit integer. Mission requirements, event triggers, conversation branches and the integration tests all read and write this one namespace:

mission "Example Delivery"
    to offer
        "combat rating" >= 200
        has "visited planet: Earth"
    on complete
        "reputation: Republic" += 10

What makes this more than a save-file dictionary is that only some conditions are actually stored. The rest are derived: the C++ registers a function against a name, and reading the condition runs that function against live game state. About 115 of these are registered across PlayerInfo and AI:

conditions["net worth"].ProvideNamed(...);
conditions["days since start"].ProvideNamed(...);
conditions["flagship planet: "].ProvidePrefixed(...);

The prefixed form is the clever half. Registering the prefix "flagship planet: " claims an entire infinite family of names: "flagship planet: Mars", "flagship planet: Luna" and every other planet, each answered by the same function inspecting the suffix. Content authors get to write a question about any planet in the galaxy without a single line of C++ being added for it.

This is the seam. Data files cannot call functions, but they can read names — so the engine exposes everything it knows as names. Adding a new fact about the world that missions can test means registering one lambda, not extending a syntax.

6Missions

There are about 2,330 mission definitions in the data files, which makes missions the largest single category of content in the game and Mission.cpp the fifth-largest source file. The design worth understanding is the split between a template and an instance.

A mission in a data file is a template, and it is often deliberately vague: deliver cargo to some planet in some region, for a fee that scales with distance. When the player walks into a spaceport, the engine finds templates whose conditions are satisfied and calls Instantiate(), which picks the random values, resolves "some planet in the Dirt Belt" to an actual planet, substitutes text, and produces a concrete mission. One template supplies an unlimited number of distinct jobs.

The detail that reveals the architecture is in a comment on a single function:

// Load a mission, either from the game data or from a saved game.

The same Load reads both. A template and a saved in-progress instance are the same class in the same format — the instance simply has all its blanks filled in. Saving a mission is writing it back out; loading a save is the ordinary content path with different input.

Missions attach to the world in two dimensions. Location decides where the player encounters the offer — the spaceport, the job board, on landing, on entering a system, or when boarding a ship. Triggers decide when the mission's own actions fire:

TriggerFires when
OFFER, ACCEPT, DECLINE, DEFERThe player is shown the mission and responds to it.
VISIT, STOPOVER, WAYPOINTThe player reaches a place the mission cares about.
COMPLETE, FAIL, ABORTThe mission ends, one way or another.
DAILYEach day that passes while the mission is active. Never has access to the interface.
DISABLEDA ship belonging to the mission is disabled.

7Two loops, one step apart

The outer loop is unremarkable: poll SDL events, step the panels, draw them, sleep until 1/60 of a second has passed. The interesting structure is one level down, in how the flight simulation gets off the drawing thread.

Engine does its physics, collision and AI work as a task on a worker thread, and the main thread talks to it through exactly three calls per frame. The state it produces is double-buffered — two draw lists, two radar snapshots — so the main thread can be drawing buffer 0 while the worker fills buffer 1.

Two details are worth keeping in mind when reading Engine. First, the main thread must never touch simulation state outside Step() — that is the window when the worker is known to be idle, which is why sprite uploads and event dispatch are wedged in there rather than anywhere more natural. Second, fast-forward is implemented in the outer loop, not the engine: it steps the panels every iteration but skips both the drawing and the frame-rate sleep on two frames out of three. The simulation runs at triple speed; the display stays at 60 frames per second.

8Panels all the way down

Everything you look at is a Panel, and panels live on a stack managed by a UI. The rule has two halves, running in opposite directions:

  • Events travel top-down. Each panel from the top of the stack is offered the event until one handles it. A panel that does not understand a key simply declines it, and it falls through.
  • Drawing travels bottom-up. The bottom panel draws first, so panels above it composite over the top. This is why a dialog can dim the flight view behind it rather than replacing it.

There are two stacks, not one. gamePanels holds the flight view and everything the player opens from it; menuPanels holds the main menu and the preferences screen. If the menu stack is non-empty it takes priority for both events and drawing, which is how the game pauses itself when you open the menu — not with a paused flag, but by having the panel that steps the simulation stop being stepped.

Panels push and pop themselves. The one piece of ceremony to know is that a popped panel is not destroyed immediately — deletion is deferred to the start of the next step, which makes it safe for a panel to pop itself from inside its own event handler. That is the ordinary case: a dialog's OK button pops the dialog.

9Ships, angles and collisions

Objects in flight share a four-level inheritance chain, and each level adds exactly one idea:

ClassAdds
DrawableA sprite, possibly animated.
BodyPosition, velocity, facing.
EntityWhat ships and minable asteroids have in common.
ShipEverything else — 5,305 lines of it.

Two things about Ship are worth stating outright, because both are load-bearing and neither is obvious.

There is no separate class for the player's ship. The flagship is a Ship like every pirate and freighter in the system; the difference is only in who issues its commands. The AI class drives all of them, including the flagship, whose keyboard input arrives through the same command mechanism the autopilot uses. This is why the autopilot can land, aim and jump for you without any special-casing — it is issuing the same commands you would.

A ship model and a flying ship are the same class. The "Aerie" entry in the shipyard catalogue and the Aerie currently taking fire in orbit are both Ship objects; buying one copies the model. That is what makes a saved ship round-trip perfectly: saving writes the same fields loading reads.

Three optimisations you will meet immediately

These show up in almost any file you open, and each looks strange until you know why.

Angle is an integer, not a number of degrees. It stores a 16-bit step count — 65,536 of them around the circle — indexing a precomputed table of unit vectors built once at startup. Rotating a vector becomes a table lookup rather than a pair of trigonometric calls, and wrapping past 360 degrees is a bitwise AND that cannot drift. Note also that angles here are clock angles: zero is up, and they increase clockwise.

Point is a pair of doubles in an SSE register. The most-used class after GameData holds a 2D vector in the processor's vector unit, so adding positions or scaling velocities is a single instruction. It is used for positions, velocities, distances and directions interchangeably.

Collision is two-stage. A CollisionSet divides the system into a grid of cells and tracks which bodies are in which, so a projectile only tests against objects in the cells it crosses. Anything that survives that is then tested against a Mask — the sprite's outline reduced to a polygon at load time, not a per-pixel comparison. Shots land where the artwork says the hull is, at polygon cost rather than bitmap cost.

10The artwork is data too

There is no sprite manifest anywhere in this project. No atlas definition, no JSON listing frames, nothing in data/ describing the images. Instead, the filename is the metadata, and the loader parses it.

A sprite is referenced from game data by a path with no extension and no frame number:

ship "Aerie"
    sprite "ship/aerie"

The loader then collects every file on disk whose name reduces to that, reading the decorations off the end of each. The rule to internalise is that a frame number is only a frame number when a blending marker introduces it — trailing digits on their own are just part of the name:

Filename ends withMeansExample from this tree
nothingA single still imageship/aaulqra.png

The markers are not evenly used: additive (840 files) and half-additive (467) dominate, because most animated art in this game is weapons fire, engine flare and explosions. Plain alpha frames number 192, and premultiplied alpha just 6. A fifth marker, ~, is the deprecated spelling of half-additive — it still loads, and logs a warning asking you to use ^.

The consequence Renaming an image file changes game behaviour, silently. Drop the + from afterburner+0.png and you have not made frame 0 opaque — you have created a still image called "afterburner0" that nothing references, and an afterburner that no longer has a sprite. There is no schema to validate against; the only check is loading every asset and looking, which is what --parse-assets does.

The payoff is that an artist adds a five-frame animated effect by dropping five correctly-named PNGs into a folder. No registration, no rebuild, no code.

11Saving and plugins

By now the shape of both of these is predictable.

A saved game is written with DataWriter, which emits the same format DataFile reads. Open one in a text editor and you will find your ships as ship nodes, your missions as mission nodes and your conditions as a flat list of name/value pairs — all of it legible, and all of it hand-editable. There is no version number to migrate and no binary layout to keep compatible: an old save loads because the loader ignores what it does not recognise and defaults what is absent.

A plugin is a directory in the player's configuration folder laid out exactly like the repository root — a data/ folder, an images/ folder, a sounds/ folder. The loader is handed a list of source directories and reads them in turn; the shipped game is just the first entry. Everything that gives plugins their power is a property of the loading rules already described:

  • Redefining merges, so a plugin can change one field of one ship.
  • Names are the only linkage, so a plugin can reference anything in the base game.
  • Load order does not matter, so a plugin can be read before or after what it refers to.
  • Unknown keys warn instead of failing, so a plugin survives a game update.

None of those were built for plugins. They are the same rules that load the shipped campaign.

12Building and checking

The build is CMake with presets. Pick the preset for your compiler — clang-cl, mingw or mingw32 on Windows, linux, macos or macos-arm elsewhere:

cmake --preset <preset>                        // configure, once
cmake --build --preset <preset>-debug          // game and tests
ctest --preset <preset>-test                   // unit tests
ctest --preset <preset>-integration            // scripted playthroughs (Linux)

Testing splits along the same data/code line as everything else. Unit tests are C++ with Catch2, and they are sharply limited: the codebase has no dependency injection, so anything that touches GameData cannot be unit tested at all. What gets covered is the self-contained machinery — the parser, conditions, formatting, geometry. Integration tests cover the rest by running the real game headless and driving it with scripts that are, inevitably, written in the game's own data format and loaded as a plugin.

There is no code formatter. Instead there are five checkers, and between them they are the project's real gate:

CheckerWhat it refuses
check_code_style.pyC++ formatting, copyright headers, include order. Reports only — it cannot fix.
check_content_style.pyData-file indentation and prose: doubled words, wrong indefinite articles, non-ASCII punctuation. The one checker that can auto-correct.
check_cmake.shSource files missing from the build lists — the invisible failure from section 2.
check_shaders.shShaders that fail to compile as both OpenGL 3.0 and OpenGL ES 3.0.
check_copyright.pyA malformed copyright file — it is a real Debian-format document, parsed strictly.

For content, the strongest check is the game itself. -p parses all data and reports errors; --parse-assets additionally loads every image and sound, which is the only way to catch a sprite whose filename does not resolve.

Pick by what you want to understand:

A suggestion, having traced these paths: do not start in source/. Open data/human/ships.txt and read a ship definition, then find the code that consumes it. In a codebase where the content outweighs the engine two to one, the data files are the specification and the C++ is the implementation — and reading them in that order means every class you meet arrives with a reason to exist already attached.
